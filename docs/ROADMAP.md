# 开发路线

## 分工

教练负责教学判断：问题是否存在、为什么优先处理、建议是否合适，以及实际训练中是否改善。

开发工作负责把这些判断整理成规则与数据结构，制作视频工具，接入模型，测试并维护 GitHub 项目。教练可以用自然语言或口述提供案例。

## 里程碑 1：一份完整的真实案例

输入：一段教练熟悉、全身和球拍尽量清晰的正手视频。先选一个教练最常处理的问题。

产物：视频时间点、观察事实、判断理由、优先级、练习建议、适用条件和改善标准。

完成条件：教练确认记录准确表达了自己的思考；缺失信息与暂不确定的部分明确保留。

入口：[教学案例模板](COACHING_CASE_TEMPLATE.md)。真实记录保存在被 Git 忽略的 `local/coaching-cases/`。

## 里程碑 2：可运行的视频复盘原型

制作本地运行的简易界面，支持打开视频、慢放、定位关键帧和添加案例标注。根据首份案例决定界面需要展示什么。

完成条件：教练能在同一个界面里指明证据并修正记录；保存后可以重新打开。

## 里程碑 3：姿态识别辅助

接入已有姿态模型，展示关键点和时间变化。用真实视频检查遮挡、快速运动和不同机位下的表现，保留人工修正入口。

完成条件：明确哪些观测在约定拍摄条件下可用，哪些仍需要教练判断。显示骨架本身不视为完成技术纠错。

## 里程碑 4：自动判断少量教学问题

收集同一问题的更多案例，包括存在问题、不存在问题、容易误判和无法判断的片段。先建立可解释规则，必要时再训练专门模型。

完成条件：在未用于开发的球员视频上，与教练独立判断比较，报告误报、漏报和无法判断的情况。评估标准在测试前约定；不把相邻帧随机分到训练与测试集。

## 里程碑 5：检查练习后的变化

记录建议、练习内容和复拍视频，在尽量一致的任务条件下比较目标动作与击球表现。

完成条件：教练与球员能判断建议是否容易执行、目标问题是否改善。早期前后对比作为探索证据，不直接宣称因果或普遍有效。

## GitHub 与本地文件夹

- `D:\tennis` 是本地工作目录，程序与文档在这里编辑。
- Git 记录每次有意义的修改，便于回看和恢复。
- GitHub 托管推送上去的版本，供其他人查看与协作。
- 关联仓库后不会自动上传所有文件；修改经过提交和推送才会出现在 GitHub。
- `local/` 用于不公开的真实视频和教学记录。公开仓库从项目说明和空白模板起步。

仓库名称和第一版界面属于可调整的工程选择。教学规则与可行性结论须根据案例逐步确认。
